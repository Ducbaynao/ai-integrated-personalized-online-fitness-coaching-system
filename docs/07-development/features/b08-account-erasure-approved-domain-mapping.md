## Fencing and completion gate

The existing Account worker locks `account_erasure_requests` by `lease_token`, rechecks mandatory hold, and calls owner cleanup only within a short transaction; S3 runs outside that transaction. PR #132 added three narrow owner ports: Workout version summaries with explicit `created_by`, nullable Nutrition meal text with explicit `created_by`, and Progress connection identifiers/credentials with explicit `user_id`. PR #133 limits Workout summaries to **unlocked** versions under V16's immutable-history guard, adds similarly scoped unlocked Nutrition version summaries, and merges V55 measurement value tombstones for the explicit `student_id` subject. This post-V55 candidate additionally clears subject-scoped batch device identifiers and photo weight values, but not their unproven notes or media. Locked summaries, raw JSON and photos remain unresolved. The SQL is idempotent and does not touch another Student's rows. A port returning normally is **not** a domain attestation: unresolved field/media groups still require persisted proof and owner review. In particular `meals` item nutrient rows, calories/macros and Student FKs survive; they are neither erased nor anonymous nor approved for indefinite retention. The media guard covers 11 known FKs, not non-FK links, S3 versions/replicas or production bucket topology. No path may set `ACTIVE_DATA_CLEANED` while any owner is unresolved, any object is unverified, or backup/provider evidence is missing. A hold committed during an in-flight S3 call cannot undo the call; the next fenced transition must stop further mutation and remain HELD/review-required.

The single current blocker/decision table is in [closure gates](b08-account-erasure-closure-gates.md#one-blockerowner-handoff-table); options there are proposals, not APPROVED policy.
