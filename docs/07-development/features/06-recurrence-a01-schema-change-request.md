## Proposed forward DDL

`V46__planned_workout_recurrence_series.sql` adds Workout-owned `workout_recurrence_series`, immutable selected `workout_recurrence_series_items`, one immutable `workout_recurrence_periods` outcome per `(series_id, block_iteration, plan_session_id)`, append-only series history, and actor-scoped command receipts. It adds nullable `planned_workouts.series_period_id` for new materializations, leaving all existing rows unchanged. A deferred period→occurrence FK permits inserting one period and its occurrence atomically in the same transaction. The selected-item composite FK prevents an outcome from referencing a session outside the selected series items. Each item now stores its source version ID and is constrained by **two composite FKs**: `(series_id, source_plan_version_id)` → series and `(plan_session_id, source_plan_version_id)` → plan session. Supporting redundant unique constraints on `(series.id, source_plan_version_id)` and `(session.id, workout_plan_version_id)` make this a database-backed invariant even for a direct SQL writer. The application still checks the effective published version and coordinates. A01 should review the two new unique indexes and FK locking/upgrade impact.

The migration extends V33's partial source-instant unique index and scheduled-overlap exclusion to rows with `series_period_id IS NOT NULL`. Older V31/V33 constraints remain. **Legacy rows outside those predicates are not covered by the new exclusion**: the Workout writer holds the Student row lock and executes the existing transactional unknown-end, source-instant and scheduled-overlap guards before inserting. A01 should verify all production writers participate in that lock order. Existing reschedule/cancel/START paths are unchanged; a terminal occurrence retains its series period link, so rerunning the job cannot recreate it.

## Lock/transaction order

Student/Trainer command: Student row → actor/current Coaching authority → actor-scoped advisory receipt lock → plan/open version → series write/history/receipt. Job: Student row → series `FOR UPDATE` → plan/open version → per-period conflict guards → period plus occurrence. The database unique/exclusion constraints are the final backstop for competing new writers. Source-version change transitions the entire series to `PAUSED_SOURCE`; an infrastructure failure rolls back and is not recorded as an ordinary skipped period. Student must confirm a **new** series against the effective published version rather than remapping the paused series.

## Upgrade and legacy audit

V46 is additive. Existing `planned_workouts.series_period_id` is null, no legacy intent or UTC end is guessed, and legacy V5 recurring Appointment rows remain untouched. Series and item tables are new, so no series-item version backfill is required. The new unique constraint on existing `workout_plan_sessions` uses its existing primary key plus non-null version ID; the FK from that column already exists. Clean-install and upgrade integration tests verify legacy nullable rows and the composite FKs; the HTTP/PostgreSQL test attempts both mismatched series-version and session-version inserts. Production upgrade should report existing duplicate or overlapping legacy rows separately, not silently delete or backfill them. A01 should check index build/lock impact and any existing orphan plan/session data before approval.
