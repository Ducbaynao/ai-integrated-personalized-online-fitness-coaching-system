# B08 linked resources — V52 A01 schema review packet (LOCAL CANDIDATE)

**A01 V52 schema decision: APPROVED, as reported by the project owner from a direct message with Person A.** The message text, timestamp and any GitHub review are not available here; this packet does not claim or quote them. Schema approval is distinct from production rollout readiness.

- Base: `origin/main@d8105eefb9156c68194d761f939c455d5ec8dfef`; highest merged migration is V51 for AI recommendation draft revisions. V52 adds nullable `messages.shared_parent_id` for the owning Workout Plan ID when the shared identity is a published version. V51 is not modified or reused.
- Existing V8 `shared_entity_type` and `shared_entity_id` remain nullable for legacy messages. V52 adds nullable `shared_guarded_v1`, then sets its default to TRUE: pre-V52 rows stay NULL, new rows are guarded. A BEFORE INSERT/UPDATE trigger forces TRUE for every new row and every edit to message/resource identity, even when SQL supplies FALSE/NULL; guarded rows cannot downgrade. This permits a non-identity UPDATE of an invalid legacy row without accepting a new invalid linked row.
- The `chat_shared_resource_shape_ck` is `NOT VALID` for existing rows, but its guarded branch is NULL-safe. `WORKOUT_SHARE` requires `WORKOUT_PLAN_VERSION`, source ID and plan parent ID. `SCHEDULE_SHARE` requires `PLANNED_WORKOUT` or `APPOINTMENT`, source ID and no parent ID. Other new message types cannot carry shared identity. `NOT VALID` alone would not preserve updates to invalid legacy rows; the guard/trigger supplies that distinction.
- No source-domain FK is added: identities belong to Workout and Schedule modules, whose lifecycle and historical rows differ. Chat verifies source existence/authority through module-owned read ports on send, replay, list and open. The DB shape constraint is not a substitute for those checks.
- Migration test `V52ChatLinkedResourceMigrationTest` exercises clean install and V51→V52 upgrade on disposable pgvector/PostgreSQL, all cross-type/NULL/parent combinations, an explicit FALSE guard bypass attempt and a valid UPDATE of an invalid legacy row. The test was RED on the old-base B08 candidate and PASS after the revised constraint; on this base it passed 2/2. HTTP/PostgreSQL `ChatNotificationIntegrationTest` passed 19/19, including linked-message insert, actor-scoped replay, source authority loss and period closure.
- The merged AI V51 changes `ai_recommendations`, not Chat columns. The merged Workout Plan query changes historical-version reads; the Chat owned-port path was exercised by the 19/19 HTTP tests, including published-version links. No B08 writer reads the AI draft schema directly.
- `ChatAccountErasureService` also clears `shared_parent_id` when it changes a sender-owned message to SYSTEM; leaving the parent would now correctly violate the new shape constraint and retain a stale source reference.
- Rollout/locking: `CREATE TRIGGER` takes `SHARE ROW EXCLUSIVE`, not `ACCESS EXCLUSIVE` on its own. The `ALTER TABLE messages` steps, especially `ADD CONSTRAINT ... NOT VALID`, require `ACCESS EXCLUSIVE`; Flyway holds the strongest acquired lock to transaction commit. `NOT VALID` avoids a legacy table scan but does not remove the DDL lock. A concrete `lock_timeout`, maintenance/low-traffic window, retry procedure and production concurrent-writer assessment have **not** been confirmed. These are deployment operations to settle, not a reversal of Person A's schema approval.
- PostgreSQL lock/`NOT VALID` basis: https://www.postgresql.org/docs/current/explicit-locking.html and https://www.postgresql.org/docs/current/sql-altertable.html. The production rollout should be measured against representative message write traffic.
