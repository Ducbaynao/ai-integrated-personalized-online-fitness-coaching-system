# A01 schema review request — B06 linked Appointment and coached proposals

Status: `CANDIDATE / A01_REVIEW_PENDING`. This document does not record A01 approval. Review the forward-only [V47 candidate](../../../services/backend/src/main/resources/db/migration/V47__linked_workout_appointment_coordination.sql) before merge; V45 and V46 remain unchanged.

## Proposed DDL and legacy upgrade

V47 adds nullable `appointment_id uuid REFERENCES fitness.appointments(id) ON DELETE RESTRICT` and `observed_appointment_version bigint` to `workout_schedule_proposal_items` and `workout_schedule_change_proposals`. A pair CHECK requires both null or a non-null ID with nonnegative version. A partial index on non-null schedule-proposal `appointment_id` supports review/audit. It neither rewrites old proposals nor manufactures an Appointment observation. Existing V45 legacy Appointment rows remain unguarded and cannot qualify for new coached materialization.

The existing V45 `appointments.planned_workout_id` is the active link held by each Appointment row; V45 does **not** by itself prove one Appointment per occurrence. V47 therefore proposes `uq_appointment_guarded_confirmed_workout_v47`, a partial unique index on non-null `planned_workout_id` for `guarded_v2 AND status='CONFIRMED'`. This blocks two new guarded confirmed rows from claiming one occurrence, including direct SQL writes, without rewriting or rejecting potentially ambiguous V5 rows (`guarded_v2=false`) during upgrade. It does **not** constrain a legacy unguarded row versus a guarded row or subsequent direct SQL updates of unguarded rows. Production writers inspect all existing confirmed links under the Student/occurrence lock; the Workout command rejects an ambiguous multi-link read rather than choosing one. A01 should decide whether an additional legacy-write gate is operationally required after auditing actual V5 links; no unknown legacy identity is backfilled here. Linked reschedule updates the qualifying row to the successor after inserting that occurrence, in the same transaction; linked cancel clears it but leaves the Appointment `CONFIRMED`. Both write append-only `appointment_events_v2` entries containing old and new occurrence IDs and Appointment versions. V33 one-successor constraint and V45 linked-workout guard remain in force. No duplicate active-link column is introduced.

Already-guarded V45/V46 rows with duplicate confirmed links would cause the new index to fail safely and roll back the upgrade. A01 should audit these rows before deployment rather than assume production has none: `SELECT planned_workout_id, count(*) FROM fitness.appointments WHERE guarded_v2 AND status = 'CONFIRMED' AND planned_workout_id IS NOT NULL GROUP BY planned_workout_id HAVING count(*) > 1`. This audit has not been run against production or local `digital_fitness`.
