# B08 account erasure — V50 A01 schema review packet (LOCAL CANDIDATE)

Base: `origin/main@27ebcf79555e0b9d09b57770a8611189765bd731` (PR #115 merged). V49 is the highest merged migration. V50 is **not applied outside disposable Testcontainers**, and no A01 sign-off is implied by CI or local tests.

## Proposed forward DDL and upgrade

`V50__account_erasure_workflow.sql` adds Account-owned request/status/lease, per-object worklist/tombstone, append-only request events, a hold record without any holder permission or endpoint, reduced push diagnostics, and evidenced audit-redaction rows. Its due-work partial index includes `HELD` for a released hold and excludes non-existent statuses. It does not alter V10's generic `data_deletion_requests` or backfill any legacy Account, Chat, notification or media row. Existing users and inboxes stay unchanged on upgrade. The request status intentionally cannot reach `ACTIVE_DATA_CLEANED` while other domain-owned PII lacks cleanup ports. The Account command/worker are default OFF.

`STORAGE_REVIEW_REQUIRED` is a V50 object-work state for bucket versioning or replica topology not verified by the adapter. It is not a successful delete, is not included in due claims, and keeps the request at `DOMAIN_REVIEW_PENDING`. The 30-day `tombstone_until` is set only for a `VERIFIED` object after deletion, never as a grace period for noncurrent bytes. This is a candidate-schema change requiring A01 review; no already-merged migration was edited.

V50 replaces only the three existing append-only triggers on `audit_logs`, `security_events` and `user_account_status_history` with restricted guards. A matching immutable correction record and SHA-256 fingerprint of the exact old row are required before only sensitive fields may be cleared; ID, event type, status/severity and timestamp remain. DELETE and any other UPDATE remain rejected. A01 should independently inspect trigger privileges, extension/schema qualification, concurrent audit insertion, JSON/email search coverage and whether other audit/evidence tables need equally scoped redaction. No broad trigger bypass or historical backfill is proposed.

Chat's sender-owned media must have a matching `media_files.owner_user_id`, a non-null bucket and a single message attachment before physical delete. Ambiguous legacy ownership or reused media is concealed immediately but placed in `OWNER_REVIEW_REQUIRED`, never guessed or reported as verified. This requires owner/A01 adjudication before the request can complete; no legacy data is backfilled by V50.

The object worklist currently covers S3 Chat media only. A legacy Chat row with another `storage_provider` is concealed through `media_files.deleted_at` but has no verified physical-delete adapter or worklist evidence. It remains part of `DOMAIN_REVIEW_PENDING`; production enablement requires an owner inventory and supported deletion/reconciliation path for every provider present in live data. Do not infer from the current S3 upload writer that all historical rows are S3.

The request transaction also clears sender-authored Chat body/shared-resource content immediately, while temporarily retaining `sender_id` as evidence for ambiguous-object adjudication. Final Chat minimization clears that sender identity, the erased actor's message read/delivery timestamps and conversation mute/last-read activity only after verified object work. The other participant's message text remains intact. `OWNER_REVIEW_REQUIRED` still blocks `ACTIVE_DATA_CLEANED`; immediate content concealment is not proof of physical object deletion.

## Locks, recovery and limits

The Account request locks `users` before disabling, joins Auth token revocation and Notification cutoff, conceals Chat media and inserts object work in one DB transaction. This serializes with new session issuance on the user row. The worker claims a request and object via `FOR UPDATE SKIP LOCKED`, writes a five-minute fenced lease, commits, then calls S3 outside the transaction; another short transaction records verified absence or a retryable failure. Expired claims can be reclaimed. A DB failure after S3 delete repeats an idempotent delete/HEAD check; object absence is verified, never presumed from a successful DELETE alone. S3 versioned historical copies/replicas are **not** proven erased by HEAD of the current key. Worker status and all exposed completion wording must keep `BACKUP_UNVERIFIED` and `PROVIDER_UNVERIFIED` distinct.

An existing valid hold stops current work and yields `HELD`; there is no product permission to place/release one. A future hold writer must lock the same request row before commit and define the race with an already-started external S3 call. That authority/lock protocol is an **open decision**, not silently granted to ADMIN. Backup configuration is only a placeholder; the 30-day per-snapshot target needs an owned lifecycle and restore drill, with erasure ledger replay before restored data is exposed.

The worker checks a hold after claiming the request and before each object claim. S3 runs after a short claim transaction, outside the DB lock; an externally inserted hold during that call cannot retract an already-started physical DELETE. The worker rechecks at its next loop iteration **even after the final object** and leaves the request `HELD` without continuing account minimization, but the object may already be absent and its work item may truthfully be `VERIFIED`. The test-only direct SQL insertion is not an approved hold writer. Before enabling, the future hold command must serialize against the request lease and explicitly decide whether to wait for an in-flight call or defer hold effectiveness; neither behavior is currently authorized.

The adapter now calls GetBucketVersioning before deleting. Any enabled/suspended/unknown versioning state fails closed before DELETE; it does not create another delete marker or infer deletion from HEAD 404. A non-versioned bucket still requires `chat.attachments.s3.erasure-topology-attested=true` before the adapter can mark origin deletion verified. That property defaults false and is only exercised in the disposable unversioned S3Mock test. Production may set it only after independent evidence of no retained replicas/versions or an approved version-aware deletion/reconciliation path; S3Mock is not proof of production topology. Missing GetBucketVersioning support or permissions is a retryable storage error, not successful erasure.

Moving `STORAGE_REVIEW_REQUIRED` back to `PENDING` by direct SQL is **not an approved recovery procedure**. A future owner-controlled operation must recheck the current hold, independently attested bucket version/replica state and object identity, then record actor, reason and before/after evidence in append-only audit before a fenced retry. Until that authority and procedure are reviewed, leave the item in storage review and keep request/worker default OFF.

**V50 deployment lock review:** PostgreSQL 18 acquires `ACCESS EXCLUSIVE` on each affected table for `DROP TRIGGER`; `CREATE TRIGGER` ordinarily acquires `SHARE ROW EXCLUSIVE`. These are different lock modes, but V50 performs DROP followed by CREATE in one transactional Flyway migration, so the stronger DROP lock remains held through commit. A queued DROP can wait behind readers/writers and, once granted, blocks both reads and writes until commit; the later CREATE does not downgrade it. A01 should schedule a short maintenance window, identify long-running transactions first, use a bounded `lock_timeout` **for the Flyway migration session only** (with a separately chosen longer `statement_timeout` if configured), and abort/retry the entire migration on lock timeout. No timeout is hard-coded into V50 and no global PostgreSQL timeout should be changed. Validate rollout and rollback timing on a production-like disposable clone; the clean/upgrade tests do not prove low-lock deployment under traffic.

**Single outstanding hold-authority decision for the project owner:** designate the specific independent role/person and approval rule allowed to place and release a mandatory hold. Recommendation for review: a separately granted privacy authority with a second-person approval for release, neither inherited from `ADMIN`; any approved writer must serialize with the request claim and record case ID, basis, scope, approver and 30-day review. Until approved, no hold mutation endpoint exists and an extant valid hold blocks the worker. The choice determines the permission contract, review audit and how an in-flight S3 deletion is fenced; it is not APPROVED by this packet.
