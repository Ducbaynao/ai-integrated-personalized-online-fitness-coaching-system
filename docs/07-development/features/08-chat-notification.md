## 2026-10-27 — Active-data export and deletion (APPROVED; implementation in progress)

The account owner may export only their account data, preferences, and Chat messages and attachment bytes **they sent**. Another participant's messages and bytes are excluded. A Trainer may export their own Chat content only while they retain current read authority for that Coaching Period; export does not reopen a former Trainer's closed-period history. A valid deletion request immediately disables the account and revokes its push tokens through current Account authority. A durable, retryable and idempotent job removes that sender's message content and attachment objects; the other participant's messages remain, without the deleted account's identifying details in the retained conversation. DB and private S3 must be reconciled explicitly: a failed S3 delete or dead worker cannot be reported as complete, and S3 calls must run outside a database transaction. These are approved product decisions, not evidence that an endpoint or worker already exists.

**Archived 2026-10-27 pre-approval note:** At that cut, no duration or mandatory-hold policy had been approved. The 2026-10-28 decisions above supersede that statement with specific 30/90/365-day minima and targets, while hold authority, backup implementation and provider-copy verification remain open. Account-owned API/state and B08-owned Chat/S3 cleanup still require explicit module ports and A01 review of forward schema. The audit below is historical, not current runtime status.

**Merged export and Account cutoff; erasure remains a local candidate:** `GET /users/me/data-export` streams a no-store ZIP of account/settings, push preferences and only actor-sent Chat facts still readable under current Chat authority. Chat and Notification expose owner-module query ports; the Account module composes the response without reading their repositories. The exporter checks active account before and throughout streaming, and never stores a ZIP or issues a presigned URL. Former-Trainer closed-period messages remain concealed. Export merged in PR #113; Account/Auth cutoff merged in PR #115. Neither is a deletion command. The V50 request/status and S3 worklist described above are local and default OFF; owner-domain cleanup and schema/upgrade review remain necessary before exposing deletion.

**Mid-stream revocation limit:** Once an account or Chat authority check fails, the exporter does not finish the ZIP or intentionally write more bytes. Entries completed before that check, and even a prefix of the current attachment, may already be in the HTTP response and remain recoverable; an incomplete archive is not a privacy boundary. The client must discard a partial response. Checks occur between chunks, so revocation cannot recall bytes sent before the next check. `ChatObjectStorage.get()` currently uses S3 `getObjectAsBytes` and loads one attachment (up to 10 MiB) into heap before the ZIP writer writes 64 KiB slices. Concurrent exports can therefore hold roughly 10 MiB per active attachment plus compression, message metadata and response buffers; this is **not** streaming from S3. Capacity/load testing and a bounded-concurrency or streaming S3 adapter are required before treating this export path as production-scale.

## M7 Attention and Review decisions — APPROVED 2026-10-18

The following are product decisions approved by Person B, **not** claims that an API, migration, scheduler, Mobile screen, or test already runs. The first review task is anchored to the start of an active human Coaching Period. Tasks recur every 14 **calendar days** in the Student-confirmed IANA timezone and each is due 7 calendar days after its own cycle start. A Trainer authorized for the current period completes a task with a summary, evidence references, and explicit missing/unknown-data information. The Student can read the result and acknowledge viewing it; acknowledgement does not gate completion. Review does not mutate Goal, Workout Plan, or Nutrition; strategic changes still use their existing commands/proposals.

`MISSED_PLANNED_V1` is a deterministic MEDIUM signal only for a still-`SCHEDULED` occurrence with known `plannedEndAt`, known absence of execution, and an end more than 24 hours in the past. Evidence identifies occurrence/version and its time interval. Null end, unknown execution state, and `RESCHEDULED`/`CANCELLED`/`SKIPPED`/other terminal occurrences produce no signal. Dedupe the same source/rule; source correction closes or supersedes it with audit, never silent deletion.

`REVIEW_OVERDUE_V1` comes only from a real review task with a due date: LOW after one calendar day, MEDIUM after seven calendar days on the *same signal*, retaining severity history. Completion or period-lifecycle cancellation resolves it with audit. An absent task or due date produces no signal. Calendar-day boundaries use the task's confirmed IANA timezone; no fixed 09:00 local-time rule was approved.

The Student reads their own signals and history. A Trainer reads or acts only on signals for an `ACTIVE` `HUMAN_COACH` period currently assigned to them, with current VIEW authority for the evidence source. Denial conceals count and detail. Trainer actions are ACK, RESOLVE and DISMISS; the latter two require a reason. Mutations use version and actor-scoped command keys, transactionally rechecking authority. Pause/end/revoke conceals immediately. Resume opens a new period and re-evaluates for that period; it never restores access to the old period's signals. Admin has no implicit coaching authority.
